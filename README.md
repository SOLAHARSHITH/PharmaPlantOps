# Plant Operations Portal

Mini digital manufacturing portal for a pharma plant. Operators and supervisors see machine health, telemetry, threshold alerts, and maintenance records.

## Decisions and assumptions

- .NET 8 Web API, EF Core, and SQL Server 2022. The schema is created on startup with `EnsureCreated`, then seeded.
- Five machines are seeded: Tablet Press 1, Coating Pan 2, Filling Line 3, Autoclave 4, and Packaging Unit 5. Each machine stores its own temperature, pressure, and speed limits.
- A background service inserts one reading per machine every 15 seconds. One machine per cycle is written over its temperature limit. An alert is created only when that machine and metric do not already have an open alert.
- Authentication is a JWT. Two users are seeded from environment variables: an Operator and a Supervisor. Passwords are stored as hashes.
- Operator can view data and acknowledge alerts. Supervisor can do that and create maintenance records.
- The external service is Open-Meteo. The dashboard shows current temperature and conditions for Exton, PA (40.029, -75.620). No API key is required. If the call fails, the API returns 503 and keeps running.
- Application Insights is enabled only when `APPLICATIONINSIGHTS_CONNECTION_STRING` is set. An empty value is valid locally.
- Integration tests use SQLite through `Database:Provider=Sqlite`. The running application uses SQL Server.
- Azure resources are defined in Bicep. Deploying them is optional.
- The walkthrough video is recorded separately. It is not generated by this repository.

## Run with Docker Compose

1. Install Docker, the .NET 8 SDK, and Node.js 22 if you want to run tests or the UI outside Compose.
2. Copy `.env.example` to `.env`. Replace the sample values before any shared environment. The sample passwords are for local sign-in only.
3. From the repository root:

```bash
docker compose up --build
```

4. Open http://localhost:3000.
5. Sign in as `operator` / `Operator123!` or `supervisor` / `Supervisor123!` unless you changed `.env`.

The API is at http://localhost:8080. Health check: http://localhost:8080/health.

SQL Server is published on localhost port 1433. The API waits until the SQL health check passes, then retries the connection while the database starts.

## Run the tests

```bash
dotnet test PlantOps.sln
```

Unit tests cover the threshold rule with Moq. Integration tests cover login, machine listing, acknowledge, and the Supervisor-only maintenance create.

## Build the UI

```bash
cd src/web
npm ci
npm run build
```

`NEXT_PUBLIC_API_URL` defaults to `http://localhost:8080`. Docker bakes that URL in at image build time.

## Secrets

Do not commit `.env`. `appsettings.json` keeps secret fields empty. Set these environment variables for the API:

- `ConnectionStrings__PlantOps`
- `Auth__JwtSigningKey` (at least 32 characters)
- `Auth__OperatorUsername` and `Auth__OperatorPassword`
- `Auth__SupervisorUsername` and `Auth__SupervisorPassword`
- `APPLICATIONINSIGHTS_CONNECTION_STRING` when telemetry should be sent

The Bicep template stores the SQL connection string, JWT signing key, and both passwords in Key Vault. The API App Service reads them with Key Vault references.

## Azure pipeline

`pipelines/azure-pipelines.yml` builds and tests the API, builds the web app, builds both Docker images, and deploys `infra/main.bicep`. Create these pipeline variables before running the deploy stage. Mark the passwords and signing key as secret.

- `AZURE_SERVICE_CONNECTION`
- `RESOURCE_GROUP`
- `SQL_ADMIN_LOGIN`
- `SQL_ADMIN_PASSWORD`
- `JWT_SIGNING_KEY`
- `OPERATOR_PASSWORD`
- `SUPERVISOR_PASSWORD`
- `DEPLOYER_OBJECT_ID` (object id allowed to write the Key Vault secrets during deployment)

## API

- `POST /api/auth/login`
- `GET /api/machines` and `GET /api/machines/{id}`
- `GET /api/machines/{id}/telemetry`
- `GET /api/alerts` and `GET /api/alerts/{id}`
- `POST /api/alerts/{id}/acknowledge`
- `GET /api/maintenance` and `POST /api/maintenance` (Supervisor)
- `GET /api/weather`
- `GET /health`
